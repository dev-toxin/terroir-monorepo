# Движок сочетаний (pairing engine)

Код: `backend/internal/pairing/engine.go`, тесты: `engine_test.go`.
Движок детерминированный и работает **без LLM**. Его результаты (оценка + причины) — первичный источник
рекомендаций; чат-ассистент получает их как «кандидатов» и только формулирует ответ.

## Принцип

- Каждая пара «вино × рецепт» начинается с **50 баллов** (`baseScore`).
- Каждое сработавшее правило добавляет или вычитает баллы и пишет **причину** (`Reason{Code, Delta, RU, EN}`).
- Итог ограничивается диапазоном **0..100**. Если ограничение не сработало, итог равен 50 + сумма всех дельт (это проверяет тест).
- Структура вина (тело/кислотность/танины 1..5, «тёмные фрукты») берётся из карточки, а если там не указано —
  из таблицы сортов `domain/grapes.go` (`ResolveStructure`), затем из значений по умолчанию для цвета.
- Сладость: dry=1, off_dry=2, medium=3, sweet=4; у десертного вина без указанной сладости считается 4.
- `TopReasons(res, locale, n)` возвращает n причин с наибольшим |delta| на RU или EN.

### 8. Профиль вкуса (`Input.Profile`, необязательный)
| Код | Условие | Дельта |
|---|---|---|
| `profile_rejected` | любой сорт вина есть в `rejected_grapes`; остальные правила профиля **не** применяются | −30 |
| `profile_liked` | сорт в `liked_grapes` (один раз) | +8 |
| `profile_dark_fruit` | `fruit_dark ≥ 4` и у вина тёмные фрукты | +6 |
| `profile_acid` | кислотность вина выше предпочтения на ≥ 2 | −8 |
| `profile_tannin` | танины выше предпочтения на ≥ 2 | −6 |
| `profile_sweet` | профиль «только сухое» (`sweetness = 1`), вино medium/sweet, блюдо не десерт | −8 |

### 9. Окно питья (`Input.Window`, необязательное; `""`/`unknown` не учитываются)
| Код | Статус | Дельта |
|---|---|---|
| `window_peak` | peak | +10 |
| `window_last_call` | last_call | +12 |
| `window_ready` | ready | +6 |
| `window_late` | late (окно прошло, лучше открыть, пока не стало хуже) | +4 |
| `window_early` | too_early | −15 |

### 10. История (`Input.Feedback` — `pairing_feedback`)
Учитываются только оценки **этой же пары** (wine_id + recipe_id). Дельта = `int((средняя − 3) · 8)`:
5 → +16 (`history_good`), 4 → +8, 3 → 0, 2 → −8 (`history_bad`), 1 → −16.
Отзыв появляется двумя путями: через «выпил» с `paired_recipe_id` и оценкой и через `POST /v1/recipes/{id}/feedback`.

## Ранжирование
- `RankWines(entries, recipe, profile, year, feedback)` оценивает бутылки с `quantity > 0` (пустые строки пропускает),
  окно питья считает по `drink_from/drink_until` на указанный год и сортирует по score; при равенстве выше бутылка с большей срочностью окна (`WindowStatus.Urgency`).
- `RankRecipes(entry, recipes, profile, feedback)` ранжирует рецепты к одной бутылке. Окно здесь не учитывается: бутылка уже выбрана.

## Как расширять
1. Новое правило добавляйте в `Score` через `s.add(code, delta, ru, en)`: код уникальный, в `snake_case`, текст на обоих языках.
2. Новый сорт добавляйте строкой в `grapeTable` (`domain/grapes.go`), при необходимости с алиасами.
3. Новый ингредиент или соус: константа в `domain/recipe.go`, запись в `known*` и строка в `ingredientAffinity`.
4. На каждое правило нужен хотя бы один табличный кейс в `TestScore_RelativeOrder` («A лучше B» плюс ожидаемый код причины).
   Точные числа в тестах не проверяйте: веса будут меняться.
5. Обновите таблицы в этом файле.

Перенос правил в YAML пока не делаем: так проще рефакторить и тестировать, а правила остаются типобезопасными. Вернуться к этому стоит, когда весами захочет управлять не программист.
